# 5. 코어 로더의 기본 파일명 및 탐색 분기 확인

## 4장에서 확정한 내용

## 5장의 내용

작업 목적. 진입 XML 후보 문자열을 만들어 선택하는 대상 버전의 분기를 찾는다.

입력. 3장에 기록한 코어 목록 생성 메서드와 4장의 설정값.

출력. 상태별 기본값, 후보 분리 규칙, 탐색 순서, 오류 처리 규칙.

## 5.1 값이 없거나 비어 있을 때의 조건을 읽는다

1. 4장에서 기록한 설정 접근 줄을 연다.
2. 그 다음에 반환값을 검사하는 조건문을 확인한다.
3. null, 길이 0, 공백 문자열이 각각 어느 분기로 들어가는지 기록한다.
4. 분기에서 조합하는 기본 파일명을 기록한다.
5. SAP 문서가 설명하는 기본 이름은 <extension>-application-context.xml이다.
6. 대상 구현에서 이 이름을 언제 검사하고 명시 설정과 어떤 우선관계를 갖는지 본문에서 확인한다.
7. <extension>-spring.xml이 소스에 있으면 그 이름이 최종 프로퍼티에 지정되었는지, 대상 코드의 별도 규칙이 있는지 확인한다.
8. 경로 후보가 선택되지 않았을 때 다음 extension을 처리하는지, 로그를 남기는지, 예외로 중단하는지 확인한다.

## 5.2 복수 리소스 문자열의 분해 규칙을 읽는다

1. 쉼표로 된 값을 분리하는 메서드를 찾는다.
2. 원래 토큰의 순서와 분리된 결과를 비교한다.
3. 토큰 양끝 공백을 제거하는지 확인한다.
4. 쉼표 뒤의 빈 토큰이나 두 구분자 사이의 빈 토큰을 유지하는지 확인한다.
5. 같은 이름이 여러 번 있으면 목록에 각각 추가되는지 또는 중복이 제거되는지 확인한다.
6. 리소스가 하나도 유효하지 않을 때 기본값을 다시 검사하는지 확인한다.
7. 대상 코드의 토큰 규칙이 확보되지 않았다면 복수 파일을 합쳐 하나로 처리하지 말고 각각 후보로 남긴다.

## 5.3 리소스 검사 순서를 읽는다

1. 목록의 각 항목에서 처음 호출하는 리소스 조회 메서드를 연다.
2. 문자열에 프로토콜이나 경로 접두사를 추가하는지 확인한다.
3. 탐색을 클래스패스에서 시작한다면 사용한 클래스 로더와 메서드 이름을 적는다.
4. 파일시스템으로 넘어간다면 그 조건과 상대 경로의 기준 디렉터리를 적는다.
5. 파일 존재를 검사하는 것과 실제 읽을 수 있는 리소스로 만드는 지점이 다르면 각각 표시한다.
6. SAP 문서는 클래스패스를 먼저 검사하고 파일시스템을 검사하는 구성을 설명한다. 대상 패치에서 확장한 분기가 있다면 그 구현을 적용한다.
7. Loading Spring configuration for 로그를 남기는 위치와 결과를 Spring에 넘기는 위치를 대조한다.
8. 로깅 전에 발견한 리소스와 실제 전달 리소스가 달라지는 분기가 있다면 결과 목록에는 실제로 전달되는 리소스를 기록한다.

## 5.5 프로그램에서의 처리 (spring-bean-analyzer-from-xml)

5장의 처리는 [spring-bean-analyzer-from-xml](../javaTool/spring-bean-analyzer-from-xml/README.md)이 한다. extension-analyzer는 5장에 관여하지 않는다.
대상 SAP 코드의 분기를 읽어 확인하지는 않고, **아래 규칙을 고정으로 적용**한다.

### 구성 위치

|소스|하는 일|
|---|---|
|`SpringLoadingAnalyzer.java`|키가 없을 때의 기본 파일명 규칙, 빈 값 처리, 값의 토큰 분리, 접두사 보완을 하고 진입 XML 후보(`Declaration`)를 만든다. `propertyRoot()`, `split()`, `hasPrefix()`|
|`SpringXmlAnalyzer.java`|각 후보 문자열을 실제 리소스 후보와 대조한다. `resolveLoadingEntry()`|

### 적용하는 규칙

|입력 사례|프로그램의 처리|기록|
|---|---|---|
|코어 키(`<ext>.application-context`)가 없음|`resources/<ext>-application-context.xml`이 있으면 그 파일을 진입 XML로 본다(`classpath:<ext>-application-context.xml`).|`evidence_kind=CONVENTION`|
|코어 키가 없고 기본 이름 파일도 없지만 `resources/<ext>-spring.xml`이 있음|진입 XML로 보지 않는다. 등록 근거가 없기 때문이다.|`REGISTRATION_NOT_ESTABLISHED`|
|전역 키(`<ext>.global-context`)가 없음|기본 파일명 규칙을 적용하지 않는다. 진입 XML 없음.|기록 없음|
|키는 있지만 값이 비었거나 구분자만 있음|진입 XML을 만들지 않고, 기본 파일명 규칙도 적용하지 않는다.|`EMPTY_LOADING_PROPERTY`|
|값이 있음|쉼표·세미콜론·공백(`[,;\s]+`)으로 나누고, 빈 토큰은 버린다. 토큰 순서를 유지하고, **같은 이름이 반복되면 각각 후보로 남긴다**(중복 제거 없음).|`evidence_kind=DECLARED_PROPERTY`|
|토큰에 접두사가 없음|앞에 `classpath:`를 붙인다.|`search_location`|
|`classpath:`/`classpath*:` 후보|선택된 extension의 `resources`, 같은 웹 컨텍스트의 `WEB-INF/classes`, 색인한 JAR에서 같은 경로를 찾는다. 후보가 여럿이면 하나를 고르지 않는다.|`CLASSPATH_CANDIDATE`, `AMBIGUOUS_CLASSPATH`, `CLASSPATH_ALL_CANDIDATE`, `NOT_FOUND_IN_SCOPE`|
|`file:`, URL, 그 밖의 프로토콜|파일시스템이나 외부 위치를 찾지 않는다.|`UNSUPPORTED_LOCATION`|
|웹: `contextConfigLocation`이 없음|Spring 기본값을 적용한다. 리스너는 `/WEB-INF/applicationContext.xml`, 서블릿은 `/WEB-INF/<서블릿 이름>-servlet.xml`|`evidence_kind=SPRING_DEFAULT_INFERRED`|
|웹: `contextConfigLocation`이 비어 있음|기본값으로 대체하지 않는다.|`EMPTY_CONTEXT_CONFIG`|

### 5장의 절과의 대응

|5장의 절|프로그램에서 하는가|내용|
|---|---|---|
|5.1 값이 없거나 비어 있을 때의 조건|**일부**|위 규칙(기본 이름 `<ext>-application-context.xml`, `<ext>-spring.xml`은 등록하지 않음, 빈 값은 기본값으로 대체하지 않음)을 고정으로 적용한다. null·빈 문자열·공백이 대상 SAP 코드에서 각각 어느 분기로 가는지, 후보가 없을 때 다음 extension으로 넘어가는지·예외로 멈추는지는 확인하지 않는다.|
|5.2 복수 리소스 문자열의 분해 규칙|**일부**|`[,;\s]+`로 나누고 빈 토큰을 버리며, 순서를 유지하고 중복을 남긴다. 실제 SAP의 분리 규칙(쉼표만인지 등)과 같은지는 확인하지 않았다. 유효한 토큰이 하나도 없을 때 기본값을 다시 검사하지 않는다.|
|5.3 리소스 검사 순서|**일부**|접두사가 없으면 `classpath:`로 보고 분석 범위 안에서 후보를 찾는다. 실제 클래스 로더의 검색 순서, 파일시스템으로 넘어가는 분기, `Loading Spring configuration for` 로그 위치와 실제 전달 리소스의 대조는 하지 않는다. 클래스패스 후보가 여럿이면 순서를 정하지 않고 `AMBIGUOUS_CLASSPATH`로 남긴다(6장과 연결).|
|5.4 분기표를 채운다|**일부**|위 「적용하는 규칙」이 프로그램의 분기표다. 기본 이름과 명시 이름이 모두 있을 때는 명시 값(키)이 있으면 그것만 쓴다. 분기별로 대상 JAR·소스의 메서드 위치를 기록하지는 않는다.|
