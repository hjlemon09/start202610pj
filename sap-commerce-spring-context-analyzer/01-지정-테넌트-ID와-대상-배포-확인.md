# 1. 지정 테넌트 ID와 대상 배포 확인

## 1장의 내용

## 1.1 설치 루트와 실제 설정 경로를 확인한다

### 목적과 조사 결과

조사할 SAP Commerce 설치와 그 설치가 사용하는 설정 파일의 위치를 정한다. 이후 테넌트, extension, Spring XML을 조사할 때 같은 배포의 자료를 사용하기 위한 단계다.

**진행 원칙:** 1.1절의 적용 대상 항목에 미확정 사항이 하나라도 남아 있으면 1.2절 및 이후 조사로 진행하지 않는다. 미확정 사항을 해소하기 위한 1.1절 내부의 확인은 계속 수행한다. 적용되지 않는 항목은 그 이유를 확인해 `해당 없음`으로 기록하며, 이를 미확정으로 취급하지 않는다.

이 절에서 사용하는 경로 이름은 다음과 같다.

|이름|뜻|예시|
|---|---|---|
|`HYBRIS_HOME`|조사 대상 SAP Commerce 설치 루트. 그 아래에 `bin\platform`이 있다.|`C:\commerce-local\hybris`|
|`CONFIG_DIR`|대상 실행이 기본 설정 디렉터리로 사용하는 경로.|표준 구성에서는 `C:\commerce-local\hybris\config`|
|추가 설정 입력|기본 설정 외에 별도로 읽는 프로퍼티 파일이나 폴더.|별도 지정된 파일 또는 폴더의 절대 경로|

`HYBRIS_HOME`과 `CONFIG_DIR`은 조사 결과를 기록하기 위한 이름이다. 같은 이름의 환경 변수가 반드시 존재한다는 뜻은 아니다. 아래 경로는 설명용이므로 실제 대상 경로로 바꾸어 사용한다.

### 1.1.1 조사할 설치 또는 배포 폴더를 연다

**왜 확인하는가**

소스 저장소와 서버를 실행하는 설치 폴더가 다를 수 있다. 먼저 받은 경로가 실제 설치인지, 소스만 있는 저장소인지 구분해야 한다.

**어떻게 확인하는가**

사용자가 지정한 경로를 파일 탐색기나 IDE에서 연다. 경로를 절대 경로로 기록하고, 그 안에서 `bin\platform`을 찾는다. 소스 저장소만 받은 경우에는 서버를 시작할 때 사용하는 `hybrisserver.bat`의 위치나 배포 폴더를 추가로 확인한다.

폴더를 찾았다고 바로 대상 설치로 확정하지 않는다. 1.1.2절에서 설치 구조를 확인하고, 1.1.4절에서 실제 시작 경로와 연결한다.

### 1.1.2 설치 구조와 버전 확인 파일을 찾는다

**왜 확인하는가**

`bin\platform`으로 설치 루트의 위치를 파악하고, `build.number`로 정확한 버전을 확인할 자료를 확보한다. 파일이 존재한다는 사실과 그 설치가 조사 대상이라는 판단은 구분한다.

**어떻게 확인하는가**

예를 들어 설치 후보가 `C:\commerce-local\hybris`라면 다음 두 항목을 각각 확인한다.

```text
C:\commerce-local\hybris\bin\platform
C:\commerce-local\hybris\bin\platform\build.number
```

`bin\platform` 폴더와 그 안의 `build.number` 파일의 존재 여부를 기록한다. 이 단계에서는 버전 자료의 위치를 확보하고, 파일 안의 실제 버전값은 **1.2절**에서 읽는다.

|번호|확인 결과|판정과 수행할 작업|이 항목의 판단 완료 조건|
|---|---|---|---|
|1.1.2-A|`bin\platform`과 `build.number`가 모두 있다.|상위 설치 루트를 설치 후보로 기록하고, `build.number`의 절대 경로를 남긴다. **1.1.4절**에서 실제 시작 경로와 연결한다.|설치 후보와 버전 확인 파일의 경로가 기록되었다. 대상 설치의 확정은 1.1.4절에서 한다.|
|1.1.2-B|`bin\platform`은 있지만 `build.number`가 없다.|실제 대상 설치의 경로를 다시 확인하고 해당 설치·배포의 `build.number`를 확보한다. 파일을 확보하기 전에는 **1.2절로 진행하지 않는다.**|대상 설치의 `bin\platform\build.number`를 열 수 있음을 확인했다. 확보하지 못하면 1.1절 미완료로 남긴다.|
|1.1.2-C|현재 폴더에 `bin\platform`이 없다.|실제 시작 명령 또는 시작 스크립트에서 `hybrisserver.bat`의 경로를 찾는다. 예를 들어 `D:\sap\hybris\bin\platform\hybrisserver.bat`를 사용한다면 `D:\sap\hybris`를 설치 후보로 삼아 **1.1.2절을 다시 수행**한다.|설치 구조를 갖춘 후보를 찾았거나, 설치 경로 확인에 필요한 시작 명령·파일을 미확정 항목으로 기록했다.|

### 1.1.3 기본 위치의 설정 파일을 각각 확인한다

**왜 확인하는가**

테넌트와 프로퍼티를 조사할 파일, 빌드의 extension 선언을 조사할 파일을 확보하기 위해서다.

여기서 확인하는 `config` 폴더는 기본 위치일 뿐, 서버가 실제로 사용하는 설정 폴더라고 아직 단정할 수 없다. 서버가 실제로 사용하는 설정 폴더(`CONFIG_DIR`)는 **1.1.5절**에서 확정한다. 따라서 이 절에서는 확인 결과만 기록하고, 아래 표 오른쪽 열의 확인은 1.1.5절을 마친 뒤 수행한다.

**어떻게 확인하는가**

1.1.2절에서 찾은 설치 후보 아래의 `config` 폴더를 열고 다음 파일을 각각 확인한다.

|파일|조사에 사용하는 내용|후속 조사 위치|
|---|---|---|
|`config\local.properties`|테넌트 관련 설정과 코어 Spring XML 선택에 영향을 주는 프로퍼티의 출처.|1.3절의 테넌트 구성 확인, 4장의 프로퍼티 최종값 확인.|
|`config\localextensions.xml`|대상 빌드가 포함할 extension을 지정·탐색하는 선언.|2장의 배포 포함 extension 확인. 실제 대상 빌드가 읽은 파일인지도 대조한다.|

|번호|확인 결과|지금 기록할 내용|1.1.5절에서 `CONFIG_DIR`을 확정한 뒤 수행할 확인|
|---|---|---|---|
|1.1.3-A|두 파일이 모두 있다.|각 파일의 절대 경로와 `존재`를 기록한다. `config` 폴더는 설정 경로 후보로 둔다.|1.1.3-A에서 확인한 `config` 폴더와 1.1.5절에서 확정한 `CONFIG_DIR`이 같은 폴더라면, 이 절에서 확인한 두 파일을 후속 조사에 사용한다. 다른 폴더라면 1.1.5절에서 확정한 `CONFIG_DIR`에서 두 파일을 다시 확인한다.|
|1.1.3-B|`local.properties`만 있다.|해당 파일의 절대 경로와 `localextensions.xml 부재`를 기록한다.|1.1.3-B에서 확인한 `config` 폴더와 1.1.5절에서 확정한 `CONFIG_DIR`이 다른 폴더라면, 1.1.5절에서 확정한 `CONFIG_DIR`에서 두 파일을 다시 확인한다. 1.1.5절에서 확정한 `CONFIG_DIR`에도 `localextensions.xml`이 없다면 대상 빌드의 대체 입력을 확인한다. 아래 「파일이 없을 때」의 절차를 따른다.|
|1.1.3-C|`localextensions.xml`만 있다.|해당 파일의 절대 경로와 `local.properties 부재`를 기록한다.|1.1.3-C에서 확인한 `config` 폴더와 1.1.5절에서 확정한 `CONFIG_DIR`이 다른 폴더라면, 1.1.5절에서 확정한 `CONFIG_DIR`에서 두 파일을 다시 확인한다. 1.1.5절에서 확정한 `CONFIG_DIR`의 `local.properties`와 추가 프로퍼티 입력을 확인한다. 필요한 설정 출처를 확보하지 못하면 관련 값은 미확정으로 둔다.|
|1.1.3-D|`config` 폴더가 없거나 두 파일이 모두 없다.|기본 위치에서 확보하지 못한 폴더·파일을 각각 기록한다.|1.1.5절에서 확정한 `CONFIG_DIR`에서 두 파일을 다시 확인한다. 그곳에도 없으면 대체 입력과 부족한 자료를 기록한다.|

**파일이 없을 때**

`localextensions.xml`이 없으면 보관된 대상 빌드 로그에서 `Extension file used:`를 검색한다. 경로가 출력되어 있다면 그 파일을 열어 대상 빌드의 입력으로 기록한다. `bin\platform\extensions.xml`은 대체 입력 후보로 확인하되, 존재한다는 이유만으로 사용된 파일이라고 판단하지 않는다. 로그나 대상 빌드 코드로 실제 사용 여부를 확인한다.

`local.properties`가 없으면 1.1.5절에서 확정한 `CONFIG_DIR`과 추가 프로퍼티 입력에서 필요한 설정을 찾는다. 파일 하나의 부재만으로 테넌트나 extension이 없다고 판단하지 않는다.

### 1.1.4 설치 후보를 실제 서버 시작 경로와 연결한다

**왜 확인하는가**

동일 PC에 설치가 여러 개라면, 폴더 구조가 정상이어도 다른 서버의 설치일 수 있다. 조사 대상 서버를 시작하는 명령과 연결된 설치를 `HYBRIS_HOME`으로 기록해야 한다.

**어떻게 확인하는가**

- **공식 `hybrisserver.bat`를 직접 실행하는 경우:** 실제 실행하는 파일의 절대 경로를 확인한다. `C:\commerce-local\hybris\bin\platform\hybrisserver.bat`라면 설치 루트는 `C:\commerce-local\hybris`다.
- **별도 시작 배치 파일이나 실행 구성을 거치는 경우:** 실제 시작 명령에서 호출하는 `hybrisserver.bat`의 절대 경로를 확인한다. 별도 설정의 지정·전달 과정을 더 조사해야 한다면 **1.1.5절의 상세 절차**를 사용한다.

실제 시작 파일이 1.1.2절에서 확인한 설치 후보에 속하면 해당 루트를 `HYBRIS_HOME`으로 기록한다. 다른 설치를 가리키면 그 설치에서 **1.1.2절과 1.1.3절을 다시 수행**한다.

시작 명령을 확인하지 못했다면 경로를 설치 후보로 유지하고, 어떤 시작 파일이나 실행 구성이 필요한지 적는다. 버전 파일을 찾았다는 이유만으로 대상 설치를 확정하지 않는다.

### 1.1.5 두 케이스에 따라 실제 설정 경로를 정한다

아래 **1.1.5.1절**에서 케이스 **1.1.5-A(별도 설정 없음)** 또는 **1.1.5-B(별도 설정 있음)**를 선택한다. 별도 설정이 없는 표준 구성은 기본 경로를 기록한 뒤 **1.1.5.6절**의 파일 확인으로 이동한다. 별도 설정이 적용되는 경우에는 **1.1.5.2~1.1.5.4절**에서 설정의 지정·전달과 추가 입력을 조사하고, 경로 선택이 불명확하면 **1.1.5.5절**을 수행한다.

`CONFIG_DIR`은 기본 설정 디렉터리이며, 추가 프로퍼티 파일·폴더는 별도 항목으로 기록한다. 이 절에 필요한 상세 절차와 기록 양식을 아래에 포함했다.

#### 1.1.5.1 별도 설정의 적용 여부에 따라 조사 경로를 선택한다

이 절은 대상 설치의 공식 `bin\platform\hybrisserver.bat`를 통해 서버를 시작하는 경우를 다룬다. 시작 방식을 CMD·IDE·서비스로 세분하지 않고, **설정 경로와 추가 프로퍼티 입력에 관한 별도 설정이 적용되는지**에 따라 다음 두 경우로 나눈다. 설정한 사람이 누구인지는 구분 기준이 아니다.

|번호|케이스|이 문서에서 수행할 내용|
|---|---|---|
|**1.1.5-A**|**별도 설정이 적용되지 않은 상태에서 공식 `hybrisserver.bat`를 직접 실행한다.**|아래 「1.1.5-A의 진행 방법」을 수행한 뒤 **1.1.5.6으로 이동한다. 1.1.5.2~1.1.5.5는 생략한다.**|
|**1.1.5-B**|**환경 변수·실행 인수·시작 구성 등으로 별도 설정이 적용된 상태에서 공식 `hybrisserver.bat`를 실행한다.**|아래 「1.1.5-B의 진행 방법」에서 조사 입력을 기록한 뒤 **1.1.5.2~1.1.5.4를 수행한다.** 경로 선택이 불명확하면 **1.1.5.5**를 수행하고, 경로를 정리한 뒤 **1.1.5.6**으로 이동한다.|

여기서 별도 설정은 기본 설정 디렉터리를 바꾸거나 추가 프로퍼티 입력을 지정하는 설정을 뜻한다. 기본 `config/local.properties`에 프로젝트 설정을 작성하는 것 자체를 1.1.5-B로 분류한다는 뜻은 아니다.

케이스가 아직 알려지지 않았다면 `케이스 미확정`으로 기록하고 1.1.5-B의 조사 절차로 입력을 확인한다. 이것은 세 번째 실행 케이스가 아니라, 조사에 필요한 정보가 아직 없는 상태다. **이미 1.1.5-A임이 알려진 환경에 1.1.5-B의 상세 조사를 반복해서 요구하지 않는다.**

**1.1.5-A의 진행 방법 — 기본 설정 경로를 사용한다**

이 케이스는 공식 시작 파일이 수정되지 않았고, 기본 설정 경로를 바꾸거나 추가 설정 입력을 지정하는 별도 설정도 적용되지 않는 표준 구성을 전제로 한다.

1. 실행하는 파일의 절대 경로를 기록한다. 예를 들어 `C:\commerce-local\hybris\bin\platform\hybrisserver.bat`다.
2. 그 파일이 속한 설치 루트를 `HYBRIS_HOME`으로 기록하고, 기본 설정 디렉터리를 `CONFIG_DIR=<HYBRIS_HOME>\config`로 기록한다. 위 예에서는 `C:\commerce-local\hybris\config`다.
3. **1.1.5.6으로 이동해** 해당 폴더의 `local.properties`와 `localextensions.xml`을 확인한다. 배치 파일의 호출 관계 추적, 환경 변수의 덮어쓰기 분석, Java 코드의 경로 결정 분석은 생략한다.

이 경우의 기록 예시는 다음과 같다.

```text
케이스: 1.1.5-A
공식 시작 파일: C:\commerce-local\hybris\bin\platform\hybrisserver.bat
HYBRIS_HOME: C:\commerce-local\hybris
CONFIG_DIR: C:\commerce-local\hybris\config
경로 판단 근거: 별도 설정이 적용되지 않는 표준 구성
추가 설정 입력: 없음
생략: 1.1.5.2~1.1.5.5
수행: 1.1.5.6의 파일 확인
```

이 절차는 표준 구성이라는 전제를 근거로 기본 경로를 사용하는 방법이다. 대상 바이너리의 분기를 디컴파일해 입증한 결과와는 근거의 종류를 구분해 기록한다.

**1.1.5-B의 진행 방법 — 별도 설정이 지정되는 지점부터 조사한다**

1. 실제 시작 명령과 설정을 지정하는 위치를 찾는다. CMD에서 설정했다면 그 CMD의 입력을, 별도 배치 파일이라면 그 파일을, IDE·서비스에서 전달했다면 해당 실행 구성을 조사 대상으로 삼는다.
2. 공식 `hybrisserver.bat`의 절대 경로와, 그 전에 실행되는 별도 시작 배치 파일이 있다면 그 파일의 절대 경로도 기록한다. 별도 배치 파일이 값을 먼저 지정한다면 1.1.5.3에서는 그 파일부터 열어야 한다.
3. 아래 결과표를 작성한다. **1.1.5-R3에 처음 열 배치 파일의 절대 경로를 기록한 시점에 1.1.5.3의 조사 시작 파일이 정해진다.** 별도 시작 배치 파일이 없으면 공식 `hybrisserver.bat`를 기록하고, IDE·서비스에서 지정한 값은 1.1.5-R1의 실행 구성에 함께 기록한다.

|번호|기록 항목|무엇을 기록하는가|
|---|---|---|
|1.1.5-R1|시작 명령과 설정 지정 위치|실제 명령, 환경 변수를 지정한 CMD 또는 IDE·서비스 실행 구성의 위치.|
|1.1.5-R2|시작 작업 폴더|시작 명령을 실행하는 작업 폴더의 절대 경로.|
|**1.1.5-R3**|**1.1.5.3에서 처음 열 배치 파일**|**별도 시작 배치 파일이 있으면 그 파일, 없으면 공식 `hybrisserver.bat`의 절대 경로.** 파일이 실제 시작 명령에 연결됨을 확인해 기록한다.|
|1.1.5-R4|공식 시작 파일과 호출 관계|공식 `hybrisserver.bat`의 절대 경로와, 별도 시작 배치 파일에서 그 파일로 이어지는 호출 위치.|
|1.1.5-R5|전달 인수|실제 전달하는 인수. 없으면 `인수 없음`.|

예를 들어 `D:\scripts\start-commerce.bat`에서 설정 경로를 지정하고 공식 `hybrisserver.bat`를 호출한다면, **1.1.5-R3은 `D:\scripts\start-commerce.bat`**다. 반면 CMD의 환경 변수로 별도 설정을 지정한 뒤 공식 파일을 직접 실행한다면 **1.1.5-R3은 공식 `hybrisserver.bat`**이며, 시작 전 환경 변수는 **1.1.5-R1**에 기록한다.

#### 1.1.5.2 시작 시점의 `HYBRIS_CONFIG_DIR` 후보값을 확인한다 — 1.1.5-B의 조사

**적용 대상과 목적**

**1.1.5-B** 또는 케이스 미확정 상태에서 수행한다. **1.1.5-A은 이 절을 생략한다.** 기본 설정 경로를 별도로 지정했는지, 지정했다면 시작 시점의 값이 무엇인지 확인한다.

**어떻게 확인하는가**

CMD에서 실행한다면 **1.1.5-R1**의 시작 명령을 실행할 CMD에서 다음 명령을 입력한다. 이 명령은 값을 조회하며 서버를 시작하지 않는다.

```bat
set HYBRIS_CONFIG_DIR
```

IDE 또는 서비스에서 설정을 전달한다면 **1.1.5-R1**에 기록한 실행 구성의 환경 변수와 상속 설정에서 같은 입력을 확인한다.

|확인 결과|이 시점에서 판단할 수 있는 것|무엇을 어떻게 확인하는가|판단 완료 조건|
|---|---|---|---|
|`HYBRIS_CONFIG_DIR=경로`가 출력됨|시작 전 CMD에 해당 값이 있다. 최종 경로는 아직 아니다.|**1.1.5.3**에서 **1.1.5-R3**의 파일을 열고 **1.1.5-R4**의 실제 호출 관계를 따라가 값의 변경·삭제·전달을 확인한다.|Java 시작 지점에 유효한 값 또는 미설정 상태를 근거 파일·위치와 함께 기록했다. 미확인 분기가 있으면 전달 상태는 미확정이다.|
|해당 변수가 정의되지 않았다는 메시지가 나옴|현재 CMD에는 이 변수가 없다. 이 결과만으로 별도 설정 전체가 없다고 판정하지 않는다.|**1.1.5.3**에서 **1.1.5-R3**부터 시작해 배치 파일 내부 지정과 **1.1.5-R5**의 인수를 조사한다. **1.1.5.4**에서 추가 프로퍼티 입력도 조사한다.|실제 시작 경로의 입력 지정 여부와 적용값을 기록했다. 자료가 부족하면 해당 입력은 미확정으로 남긴다.|
|당시 CMD 또는 시작 환경을 확인할 수 없음|새 CMD의 값으로 과거 실행의 입력을 확정할 수 없다.|**1.1.5-R1**의 당시 실행 구성, **1.1.5-R3**의 보관된 배치 파일, 해당 기동 시점의 로그에서 입력값 또는 실제 선택 경로의 근거를 찾는다.|당시 입력 상태 또는 실제 경로를 보여 주는 근거를 확보했다. 확보하지 못하면 부족한 자료와 미확정 상태를 기록한다.|

이 절의 판단 완료는 입력 상태에 관한 것이다. 최종 경로는 별도 설정의 전달·선택 결과까지 연결해 기록한다. 1.1.5.4는 추가 입력을 확인하는 절이며 기본 경로를 확정하는 절은 아니다. 경로 선택 근거가 부족하면 1.1.5.5에서 대상 코드를 조사하고, 그 자료도 부족하면 미확정으로 남긴다.

#### 1.1.5.3 배치 파일에서 값이 설정·변경·전달되는 과정을 따라간다 — 1.1.5-B의 조사

**1.1.5-A은 생략한다.** 1.1.5-B 또는 케이스 미확정 상태에서 아래 절차를 수행한다.

**왜 확인하는가**

문자열 검색으로 발견한 경로가 실제 적용값이라는 보장은 없다. 주석이나 실행되지 않는 조건문 안에 있을 수 있고, 뒤에서 다른 값으로 바뀌거나 지역 환경 범위가 끝나면서 사라질 수도 있다.

**어떻게 확인하는가**

1. **1.1.5-R3**에 기록한 배치 파일을 편집기로 연다. 별도 시작 배치 파일이 있으면 그 파일을, 없으면 공식 `hybrisserver.bat`를 연다. `HYBRIS_CONFIG_DIR`을 검색해 대입·전달하는 줄을 찾는다. **1.1.5-R4**의 호출 관계와 **1.1.5-R5**의 실제 인수를 기준으로 이후 실행 분기를 확인한다. IDE·서비스에서 먼저 지정한 값은 **1.1.5-R1**의 실행 구성과 대조한다.
2. 발견한 줄이 주석인지 실행문인지 구분한다. `if`, `goto`, 전달 인수에 따른 분기를 읽어 대상 시작 명령이 실제로 그 줄을 거치는지 확인한다.
3. 다른 `.bat` 파일을 호출하면 그 파일을 연다. 호출된 파일 안에서도 같은 변수를 검색하고, 호출 후 원래 파일로 돌아와 이후 대입문까지 확인한다.
4. `setlocal`과 `endlocal`이 있다면 Java를 시작하는 지점에서 어떤 값이 유효한지 확인한다. 파일 중간에서 잠시 설정된 값만 기록하지 않는다.
5. 환경 변수 외에 Java 시스템 프로퍼티나 별도 부트스트랩 설정으로 값을 전달하는 코드가 보이면 그 전달 방식도 기록한다. 환경 변수와 `-D키=값`은 서로 다른 입력이므로 실제 조회 코드에서 어떻게 연결되는지 확인한다.
6. 최종 실행 명령 또는 실행 설정을 만드는 파일까지 따라가 어떤 값이 다음 프로세스에 전달되는지 정리한다.

예를 들어 아래 코드가 대상 실행에서 실제로 수행된다면 `local-a`가 기본 설정 경로의 후보가 된다.

```bat
set "HYBRIS_CONFIG_DIR=D:\sap-config\local-a"
call "C:\commerce-local\hybris\bin\platform\hybrisserver.bat"
```

이후 호출 경로에서 값이 유지되고, 대상 경로 결정 코드가 이 입력을 사용한다는 것까지 확인해야 최종 경로로 확정할 수 있다.

변수나 상대 경로가 포함된 경우에는 다음 기준으로 절대 경로를 계산한다.

|경로 표현|계산 방법|예시 또는 확인할 근거|
|---|---|---|
|`%~dp0` 포함|그 표현이 들어 있는 배치 파일 자체의 드라이브와 디렉터리를 대입한다.|`D:\scripts\start.bat`의 `%~dp0config`는 `D:\scripts\config`를 가리킨다.|
|`%변수명%` 포함|대입문이 실행되는 시점의 변수값을 확인한다.|변수의 정의 위치와 중간 덮어쓰기를 함께 기록한다.|
|`!변수명!` 포함|지연 확장 사용 여부와 해당 명령 실행 시점의 값을 확인한다.|블록 안에서 값이 바뀐다면 `%변수명%`과 같은 결과라고 가정하지 않는다.|
|`..\config` 같은 상대 경로|해당 경로를 실제로 해석하는 명령 또는 Java 코드의 기준 폴더를 확인한다.|앞선 `cd`, `pushd`, 실행 구성의 작업 폴더 및 코드의 경로 조합을 확인한다.|

배치 파일이 있는 폴더와 현재 작업 폴더는 다를 수 있다. 특히 상대 경로를 무조건 배치 파일 위치 기준으로 계산하지 않는다.

**남길 근거**

각 대입·전달 위치의 파일과 줄, 그 줄이 실행되는 조건, 변경 전후 값, 절대 경로 계산에 사용한 기준을 기록한다.

#### 1.1.5.4 기본 경로 외에 추가로 읽는 프로퍼티 입력을 확인한다

**1.1.5-A은 생략한다.** 1.1.5-B 또는 케이스 미확정 상태에서 수행한다.

**왜 확인하는가**

`CONFIG_DIR`을 찾았더라도 `local.properties`만 읽어서는 최종 설정값을 알 수 없는 배포가 있다. 별도 파일이나 폴더의 프로퍼티가 함께 합쳐지면 테넌트 설정과 Spring XML 선택에 영향을 주는 키의 값이 달라질 수 있다.

SAP 문서는 `HYBRIS_RUNTIME_PROPERTIES`로 추가 프로퍼티 파일을, `HYBRIS_OPT_CONFIG_DIR` 또는 `hybris.optional.config.dir`로 선택적 설정 디렉터리를 지정하는 방식을 설명한다. 다음 절차로 실제 대상 배포의 적용 여부를 확인한다. [SAP Commerce Runtime and Optional Configuration](https://help.sap.com/docs/SAP_COMMERCE/b490bb4e85bc42a7aa09d513d0bcb18e/8beb75da86691014a0229cf991cb67e4.html)

**어떻게 확인하는가**

1. 시작 배치 파일, 그 파일이 호출하는 파일, 실행 구성의 환경 변수에서 `HYBRIS_RUNTIME_PROPERTIES`와 `HYBRIS_OPT_CONFIG_DIR`을 검색한다.
2. 대상 배포의 프로퍼티 파일과 부트스트랩 설정에서 `hybris.optional.config.dir`을 검색한다. 발견된 파일이 해당 키를 조회하기 전에 읽히는지도 로딩 코드에서 확인한다.
3. 값을 발견하면 1.1.5.3과 같은 방법으로 덮어쓰기와 경로 해석을 확인한다. 실제 적용되는 파일·폴더의 절대 경로를 구한다.
4. 추가 파일은 존재 여부와 읽을 수 있는지 확인한다. 추가 폴더는 파일 목록을 확인한 뒤 대상 버전의 로더가 선택하는 이름 패턴과 처리 순서에 맞춰 입력 목록을 정리한다. 단순히 폴더에 있는 모든 파일을 적용 대상으로 넣지 않는다.
5. 동일 키가 여러 입력에 있으면 원문과 출처를 모두 남긴다. 최종값을 확정하려면 대상 로더의 병합 순서와 우선순위를 확인한다.

|입력 항목|확인할 대상|기록할 결과|
|---|---|---|
|`HYBRIS_RUNTIME_PROPERTIES`|지정된 추가 프로퍼티 파일과 그 값을 전달한 시작 구성|원문 값, 파일 절대 경로, 존재·읽기 가능 여부, 실제 로딩 근거.|
|`HYBRIS_OPT_CONFIG_DIR`|환경 변수로 지정한 추가 설정 폴더|원문 값, 폴더 절대 경로, 로더가 선택한 파일과 처리 순서의 근거.|
|`hybris.optional.config.dir`|프로퍼티로 지정한 추가 설정 폴더와 해당 키의 조회 시점|정의 파일·줄, 적용값, 환경 변수와 동시에 지정됐을 때의 선택 결과와 근거.|

이 파일·폴더들은 `CONFIG_DIR`과 별도 항목으로 기록한다. 추가 설정 폴더를 발견했다는 이유로 기본 설정 디렉터리를 그 경로로 바꾸어 기록하지 않는다.

**남길 근거**

각 입력의 경로, 지정 위치, 실제로 읽는 파일 목록, 처리 순서와 아직 확인하지 못한 우선순위를 기록한다. 입력을 발견하지 못했다면 어디까지 조사했는지 적는다. 상위 환경을 확인하지 못한 경우에는 추가 입력이 없다고 확정하지 않는다.

#### 1.1.5.5 대상 버전의 Java 코드에서 최종 경로 선택을 확인한다

**1.1.5-A은 생략한다.** 1.1.5-B의 설정 경로 선택이 시작 구성과 확보된 근거만으로 명확하지 않을 때 수행한다. 해당 실행에서 선택된 경로를 직접 보여 주는 근거를 이미 확보했다면 그 근거를 기록하고 1.1.5.6으로 이동할 수 있다.

**왜 확인하는가**

시작 구성은 입력값을 보여 주지만, 그 입력을 어떤 우선순위로 읽고 기본 경로를 어떻게 만드는지는 대상 구현이 결정한다. 별도 지정이 검색되지 않았다는 이유만으로 `<HYBRIS_HOME>\config`를 확정하면 상위 입력이나 커스텀 분기를 놓칠 수 있다.

**어떻게 확인하는가**

1. IntelliJ의 클래스 검색에서 `de.hybris.bootstrap.config.SystemConfig`를 연다. 소스가 없다면 대상 배포의 JAR에 있는 클래스를 열어 디컴파일 결과를 확인한다. 다른 설치나 다른 패치의 동명 클래스를 열지 않았는지 JAR 경로를 확인한다.
2. `getConfigDir()`로 이동해 반환하는 필드 또는 계산식을 찾는다. SAP 2211.4 공개 API에는 이 메서드와 `PROPERTY_CONFIG_DIR` 상수가 나와 있으나, 실제 경로 결정 분기는 대상 코드에서 확인해야 한다. [SystemConfig API](https://help.sap.com/doc/789b8a6e1434444da824c2493c6faaa0/2211.4/en-us/de/hybris/bootstrap/config/SystemConfig.html)
3. 반환값이 필드라면 해당 필드의 쓰기 위치를 찾는다. IntelliJ의 `Find Usages`로 대입 지점·생성자·초기화 메서드를 확인한다.
4. 다른 메서드의 반환값을 대입한다면 그 메서드로 이동한다. 키를 상수로 표현하면 상수값도 확인한다. 설정 객체에서 읽는다면 그 객체를 생성하고 값을 채우는 호출자까지 따라간다.
5. 실제로 읽는 입력이 OS 환경 변수인지, JVM 시스템 프로퍼티인지, 별도 설정 객체인지 확인한다. 1.1.5.2~1.1.5.3에서 찾은 값이 그 입력까지 전달되는지 대조한다.
6. 입력이 없을 때의 분기를 읽는다. 설치 루트나 플랫폼 경로를 어떻게 조합하는지 확인한 뒤 실제 대상 경로를 대입한다. 그 결과가 `C:\commerce-local\hybris\config`라면 해당 경로와 계산 근거를 기록한다.
7. 여러 입력이 있을 때 어떤 값을 먼저 선택하는지 확인한다. 빈 문자열과 미설정 상태를 구분하는 조건이 있다면 대상 입력이 어느 분기에 들어가는지도 적는다.

**남길 근거**

소스 또는 JAR의 절대 경로, 클래스 전체 이름, 메서드, 입력 키, 선택 조건과 최종 경로를 기록한다. 디컴파일 결과에 원본 줄 번호가 없다면 메서드와 해당 조건문을 식별할 수 있게 남긴다. 필요한 구현을 확보하지 못했다면 후보 경로와 부족한 클래스·메서드를 적고 미확정으로 유지한다.

#### 1.1.5.6 선택한 설정 경로에서 후속 조사 파일을 확인한다

**1.1.5-A과 1.1.5-B 모두 수행한다.** 1.1.5-A은 기본 CONFIG_DIR을, 1.1.5-B는 조사해 특정한 CONFIG_DIR을 사용한다. 경로가 미확정이면 파일은 후보로만 기록한다.

**왜 확인하는가**

앞서 기본 위치에서 찾은 파일과 실제 서버가 읽는 파일이 다를 수 있다. 최종 경로를 확인한 뒤 조사 입력을 연결해 두어야 다음 절에서 다른 폴더의 설정값을 섞어 쓰지 않는다.

**어떻게 확인하는가**

1. 1.1.5-A에서 기록한 기본 `CONFIG_DIR` 또는 1.1.5-B에서 특정한 `CONFIG_DIR`을 파일 탐색기나 IDE에서 연다.
2. 그 안의 `local.properties`와 `localextensions.xml`을 각각 확인한다. 파일별로 존재 여부와 절대 경로를 기록한다.
3. **1.1.3절**에서 확인했던 기본 위치와 다르면 실제 `CONFIG_DIR`의 파일로 조사 입력을 갱신한다.
4. 파일이 없으면 부재를 기록하고 해당 파일의 대체 입력이나 생성 경로를 확인한다. 경로가 선택됐다는 것과 필요한 파일이 존재한다는 것은 따로 판정한다.
5. `localextensions.xml`은 이후 extension 조사에서 대상 빌드가 사용한 파일과도 대조한다. 서버 시작 시점의 설정 경로만으로 과거 빌드의 입력 파일까지 확정하지 않는다.

### 1.1.6 서로 다른 경로가 발견되면 실제 적용값을 구분한다

**적용 대상:** 1.1.5-B에서 설정 경로 후보가 여러 개 발견된 경우에 수행한다. 1.1.5-A은 생략한다.

**왜 확인하는가**

여러 파일에 적힌 경로 중 어느 것이 적용되는지 확인하지 않으면 잘못된 파일을 조사하게 된다. 또한 기본 설정 폴더와 추가 프로퍼티 폴더는 동시에 사용될 수 있으므로 서로 다른 경로가 있다는 이유만으로 충돌이라고 판단해서도 안 된다.

**어떻게 확인하는가**

각 경로에 대해 ‘지정 위치, 실제 실행 조건, 뒤쪽 덮어쓰기, 값을 읽는 코드’를 연결한다. 다른 환경용 분기나 실행하지 않는 구성은 대상 입력에서 제외하고 그 이유를 기록한다. 기본 경로와 추가 입력이 함께 적용된다면 둘을 별도 항목으로 남긴다.

최종 적용값을 결정하지 못하면 후보를 임의로 선택하지 않는다. 어떤 파일·환경 변수·코드가 부족한지 적고 영향을 받는 경로만 미확정으로 둔다.

### 1.1.7 소스와 실제 배포가 분리되어 있다면 대응 관계를 기록한다

**왜 확인하는가**

현재 저장소의 파일과 대상 서버에 배포된 파일이 서로 다른 빌드에서 나왔을 수 있다. 소스 조사 결과를 실제 배포의 근거로 사용하려면 둘의 대응 관계가 필요하다.

**어떻게 확인하는가**

소스 저장소 경로와 실제 설치·배포 경로를 각각 기록한다. 대상 배포의 빌드 자료나 배포 메타데이터에서 커밋, 빌드 번호, 배포 식별자를 찾고 소스 기준과 대조한다. 대응 관계를 확인하지 못했다면 소스와 배포의 경로·식별자를 따로 남기고, 동일 버전이라고 가정하지 않는다.

소스와 배포가 분리되어 있지 않다면 그 사실을 기록하고 별도 경로 대조는 생략한다.

### 이 절에서 남길 기록

`기록 대상` 열에 따라 기록한다.

- **전체:** 항상 기록한다.
- **1.1.5-A 제외:** 1.1.5-A는 입력하지 않는다.
- **해당할 때만:** 1.1.5-A 여부와 관계없이 표에 적힌 조건이 성립할 때만 기록한다. 조건이 성립하지 않으면 입력하지 않는다.

|기록 항목|기록 대상|실제 값|근거와 상태|
|---|---|---|---|
|대상 `HYBRIS_HOME`|전체| |실제 시작 파일과 연결된 경로. 연결을 확인하지 못했다면 설치 후보.|
|공식 `hybrisserver.bat`|전체| |절대 경로와 실제 시작 명령.|
|버전 확인 파일|전체| |대상 설치의 `bin\platform\build.number` 절대 경로와 읽기 가능 여부. 버전값은 1.2절에서 확인.|

|1.1.5절에서 확정한 `CONFIG_DIR`|전체| |1.1.5-A는 `<HYBRIS_HOME>\config`와 표준 구성이라는 판단 근거. 1.1.5-B는 별도 설정의 적용 근거.|

### 완료 기준

다음 조건을 모두 충족했을 때만 **1.2절로 진행한다.**

|확인 항목|1.1절의 완료 조건|
|---|---|
|대상 설치|실제 시작 파일과 `HYBRIS_HOME`의 연결을 확인했다.|
|버전 확인 파일|해당 설치의 `bin\platform\build.number`를 확보했고 열 수 있다.|
|설정 케이스와 `CONFIG_DIR`|1.1.5.1절에서 설정 케이스(1.1.5-A 또는 1.1.5-B)를 선택하고, 1.1.5절에서 확정한 `CONFIG_DIR`과 판단 근거를 기록했다.|
|설정 파일|실제 경로에서 `local.properties`와 `localextensions.xml`의 존재 여부를 확인했다. 파일이 없다면 실제 대체 입력 또는 부재 시 처리 근거까지 확인해 입력 위치가 미확정으로 남지 않았다.|
|추가 설정 입력|1.1.5-B: 적용되는 파일·폴더를 특정했거나, 추가 입력이 없음을 기록했다. 1.1.5-A는 이 항목을 확인하지 않는다.|
|경로 충돌과 소스·배포 관계|1.1.6~1.1.7절의 적용 대상이면 확인을 마쳤다. 적용되지 않으면 이유와 함께 `해당 없음`으로 기록했다.|

**위 항목 중 하나라도 미확정이면 1.1절은 미완료다.** 부족한 파일·설정·근거와 이를 확인할 위치를 기록하고, 1.1절 안에서 해당 항목을 해결한다. 미확정 상태로 1.2절이나 이후 장을 먼저 수행하지 않는다.

1.1.5절 안의 입력 확인 또는 파일 확인을 마쳤더라도, 위 조건을 모두 충족하기 전에는 1.1절 전체를 완료한 것으로 판정하지 않는다.

## 1.2 정확한 SAP Commerce 버전을 확인한다

**진행 조건:** 1.1절의 완료 조건을 모두 충족한 상태에서 수행한다. 이 절에서는 1.1절에서 확보한 대상 설치의 `build.number`를 기준으로 버전을 기록한다.

1. `<HYBRIS_HOME>\bin\platform\build.number`를 연다.
2. `version=` 항목의 값 전체를 기록한다. `2211`처럼 일부만 옮기지 말고, 파일에 적힌 패치 번호와 접미사를 포함해 그대로 기록한다.

### 기록 예시

|항목|기록할 값|
|---|---|
|버전 원문|`version=<파일에 적힌 값 전체>`|
|파일 경로|`C:\commerce-local\hybris\bin\platform\build.number`|

1.1절에서 확인한 파일을 열 수 없거나 `version=` 값을 읽을 수 없으면 1.2절을 완료하지 않는다. 1.1절의 파일 확보 상태를 다시 확인하고, 버전값을 기록한 뒤 후속 절로 진행한다.

## 1.3 지정 테넌트가 대상 배포에 구성되는지 확인한다

1. 입력받은 테넌트 ID 원문을 기록한다. 대소문자나 공백의 처리 규칙이 결과에 영향을 주는 경우 대상 코드가 실제로 하는 처리를 확인한다.
2. CONFIG_DIR/local.properties와 HYBRIS_HOME/bin/platform/project.properties에서 installed.tenants를 검색한다.
3. 파일에 값이 여러 번 나오거나 외부 배포 설정이 같은 키를 덮어쓰면 최종 적용값과 출처를 기록한다.
4. 입력받은 테넌트 ID가 master라면 SAP Commerce 기본 테넌트 규칙과 대상 설치를 근거로 기록한다.(master는 별도 지정이 없어도 테넌트가 기본구성됨)
5. 추가 테넌트를 지정했다면 최종 installed.tenants 및 실제 레지스트리 구성 코드에서 그 ID가 구성 대상인지 확인한다.
6. 추가 테넌트 파일의 표준 확인 위치는 HYBRIS_HOME/bin/platform/tenant_<ID>.properties와 CONFIG_DIR/local_tenant_<ID>.properties다.
7. 같은 ID의 파일이 둘 다 있으면 Utilities.getTenantInfos()를 탐색 지점으로 삼아, 대상 빌드에서 파일을 읽고 합치는 코드와 적용 우선순위를 확인한다.
8. 커스텀 코드나 별도 배포 설정으로 테넌트를 구성하는 경우, 대상 Registry 또는 부트스트랩 코드에서 ID를 추가하는 분기와 그 입력을 확인한다.
9. 파일의 존재, 설치 설정의 등록 여부, 런타임 초기화 상태를 서로 다른 값으로 기록한다.
10. 이 단계에서는 지정 테넌트의 구성 및 정적 재현에 필요한 입력을 확인한다.

|결과                                             |판정                               |
|-----------------------------------------------|---------------------------------|
|입력받은 테넌트가 `master` (master는 자동구성됨)                    |기본 테넌트로 기록한다.                    |
|`demo`가 최종 구성에 있고 해당 테넌트의 설정 원본을 확보함           |`demo`와 파일 출처를 확정한다.             |
|`tenant_demo.properties`만 있고 최종 구성에 포함되는 근거가 없음|파일을 설정 후보로 기록하고 테넌트 등록은 미확정으로 둔다.|
|지정 ID가 최종 구성에 없고 별도 등록 경로도 없음을 확인함             |해당 배포에 구성되지 않은 테넌트로 기록한다.        |

## 1.4 프로그램에서의 처리 (고정값)

[extension-analyzer](../javaTool/extension-analyzer/README.md)와 [spring-bean-analyzer-from-xml](../javaTool/spring-bean-analyzer-from-xml/README.md)은 1장의 조사를 하지 않고, 아래 값을 **고정값(전제)으로 사용**한다.
1장에서 확인한 실제 배포가 이 전제와 다르면 프로그램 결과를 그대로 쓰지 않는다.

|1장의 항목|프로그램이 쓰는 값|바꾸는 방법|
|---|---|---|
|`HYBRIS_HOME` (1.1)|extension-analyzer 실행 인자. 생략하면 `C:\hybris`. spring-bean-analyzer-from-xml은 extension-analyzer 결과의 `hybris_home`을 그대로 쓰고, 다른 경로를 주면 오류로 끝난다.|extension-analyzer의 첫 번째 인자|
|`CONFIG_DIR` (1.1)|`<HYBRIS_HOME>/config` 고정. `localextensions.xml`과 `local.properties`를 여기서 읽는다.|`-Dextractor.localextensions=<파일>`(extension-analyzer), `-Danalyzer.localproperties=<파일>`(spring-bean-analyzer-from-xml)|
|추가 설정 입력 (1.1)|읽지 않는다. 환경 변수, JVM 시스템 프로퍼티, 배포 시 치환·생성되는 설정은 반영하지 않는다.|없음|
|설치와 실제 서버 시작 경로의 대응 (1.1.4~1.1.7)|확인하지 않는다. 지정한 설치 폴더가 곧 실행 배포라고 본다.|없음|
|SAP Commerce 버전 (1.2)|확인하지 않는다. 2211의 규칙을 전제로 판정한다.|없음|
|테넌트 (1.3)|`master` 고정. 코어 컨텍스트는 `CORE` 하나만 모델링한다. `installed.tenants`, `tenant_<ID>.properties`, `local_tenant_<ID>.properties`는 읽지 않는다.|없음|

따라서 프로그램 결과는 "지정 설치 폴더 = 실행 배포, 버전 2211, 테넌트 master"일 때의 정적 추정이다.
